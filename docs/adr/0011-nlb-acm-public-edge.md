# ADR 0011: NLB + ACM for the public edge, ExternalDNS for app records

## Status

Accepted

## Context

Spec 011 ("Public Edge") originally bundled the AWS-side public edge into a
single ALB-shaped design: AWS Load Balancer Controller provisioning an ALB
from a Kubernetes `Ingress`/Gateway API resource, ACM TLS termination at the
ALB, and an implementation *hint* (not a requirement) suggesting
ExternalDNS for the DNS records. A review of that spec against
architecture.md, the constitution, and the other public-edge specs surfaced
several gaps: no IAM/Pod Identity requirement for either new controller, no
hard commitment to ExternalDNS (Requirement 7 was controller-agnostic), no
guard against ExternalDNS deleting Terraform's ACM DNS-validation record in
the same hosted zone, and an explicitly unresolved question about whether
the AWS-side trigger resource should be an `Ingress` or a Gateway API
`Gateway`.

Separately, the operator prefers an NLB in front of Envoy Gateway over an
ALB. Two ways to terminate TLS on an NLB were compared:

1. **NLB with an ACM TLS listener** — TLS terminates at the NLB using the
   existing persistent ACM certificate (spec 002/ADR 0002), plaintext to
   Envoy Gateway behind it.
2. **NLB with TLS terminated inside Envoy via cert-manager** — cert-manager
   issues a Let's Encrypt certificate (DNS-01 against the lab Route 53
   zone, since the wildcard SAN requires it), loaded into Envoy as a
   Kubernetes Secret.

Option 2 was rejected for three concrete reasons, not general distaste for
cert-manager:

- **ACM certificates cannot be used this way at all.** An ACM certificate's
  private key is not exportable — it can only be attached to an AWS-managed
  load balancer (ALB, NLB TLS listener, CloudFront), never loaded into a
  pod. Terminating TLS inside Envoy therefore requires an entirely
  different certificate source; ACM is not an option to "reuse."
- **Let's Encrypt's duplicate-certificate rate limit (5 identical-SAN-set
  certificates per week) collides directly with this platform's own CI.**
  Spec 019 (CI Full Lifecycle Validation) deliberately runs
  `make up` → `make down` → `make up` cycles as its acceptance test. Every
  cycle would request an identical `lab.<root-domain>`/`*.lab.<root-domain>`
  certificate if the Kubernetes Secret holding it doesn't survive — and it
  can't survive by default, since Secrets live in etcd, which is destroyed
  with the disposable EKS cluster. Six recreate cycles in a week and
  issuance is blocked mid-CI.
- **Reusing one certificate across recreations requires new, unproven
  plumbing.** cert-manager only adopts an existing certificate if a valid
  matching Secret is already present when it reconciles. Making that true
  again after a full EKS destroy/recreate means round-tripping the
  cert/key material through something persistent (Secrets Manager) and
  restoring it before cert-manager starts — a bridge this repository has no
  precedent for (its existing Secrets Manager flow is one-directional,
  external-to-cluster). This is the same *class* of problem ADR 0010 solved
  for the Postgres EBS volume, and that took a whole ADR plus a dedicated
  Terraform module. Building an equivalent bridge for a TLS Secret is a
  real, non-trivial cost, not a spec-writing exercise.

Option 2 would also have required rewriting constitution §14 and
superseding ADR 0002 (both currently commit to ACM/Terraform-owned,
persistent-lifecycle certificates), and adds a third writer
(`_acme-challenge` TXT records) into the same Route 53 hosted zone
alongside Terraform's own validation record and the app-hostname records
now assigned to ExternalDNS.

## Decision

**NLB with an ACM TLS listener.** No cert-manager, no Let's Encrypt. ADR
0002 and constitution §14 are unchanged by this decision — the ACM
certificate remains Terraform-owned, Persistent-lifecycle, DNS-validated,
exactly as already specified. This ADR renames a mechanism (ALB → NLB) and
tightens ownership wording across the constitution, `CLAUDE.md`, and
specs 010/011/014; it does not reverse any existing certificate decision.

**No AWS-side `Ingress` or `Gateway` resource at all.** AWS Load Balancer
Controller provisions the NLB directly from Envoy Gateway's own `Service`
(generated by its `EnvoyProxy` resource, spec 010), using `target-type: ip`
to register Envoy pod IPs. There is nothing at the AWS layer for a second
routing resource to duplicate — Gateway API, via Envoy's own `HTTPRoute`s,
is the only routing definition anywhere in this design. This resolves spec
011's previously open "Ingress vs. Gateway API" question by removing the
AWS-side resource that made the question exist in the first place: chaining
AWS Load Balancer Controller's own Gateway API support to Envoy's Gateway
API resources would have forced host/path routing decisions into the AWS
layer too, which constitution §8 forbids.

**Ownership split on the `EnvoyProxy` resource.** Spec 010 owns the
resource's existence and shape, including a `protocol: HTTP` listener with
no `tls` block (TLS ends at the NLB; Envoy never holds a certificate).
Spec 011 owns only the `aws`-target annotation *values* injected into
`EnvoyProxy.spec.provider.kubernetes.envoyService.annotations` — ACM ARN,
`nlb-target-type: ip`, `ssl-ports`, `proxy-protocol-v2` — supplied via
`values-aws.yaml`. Two specs, one generated object, an explicit line
between "what it is" and "what values it carries on `aws`."

**ACM ARN wiring reuses ADR 0010's pattern.** NLB has no host-based ACM
auto-discovery (unlike ALB matching `Ingress` host rules against
certificate SANs), so the ARN must be explicitly wired: a Terraform output
from spec 002 → an `argocd-bootstrap` Helm parameter → `gitops/values.yaml`
→ templated into the `EnvoyProxy` annotation — the same
Terraform-output-to-gitops-value path ADR 0010 built for the Postgres EBS
volume handle, not a hardcoded account-specific literal in committed YAML.

**Proxy Protocol v2 is load-bearing, not decoration.** An NLB TLS listener
terminates the connection, so without Proxy Protocol v2 every request
appears to Envoy to originate from the NLB itself — silently defeating spec
010's per-client rate-limiting requirement, not merely losing log fidelity.
Spec 011 requires it on both the NLB target group and Envoy's `EnvoyProxy`
config.

**No port 80, no HTTP→HTTPS redirect at the AWS layer.** An ALB provides
this for free; an NLB TLS listener does not, and adding an L7 redirect
component at the edge would reintroduce the routing-duplication problem
this design otherwise avoids. `http://` requests to a `*.lab.<root-domain>`
hostname simply fail to connect. Accepted, stated behavior for a lab.

**ExternalDNS is promoted from an implementation hint to its own spec
(012), with a hard ownership guarantee.** It reads hostnames via
`--source=gateway-httproute` directly from spec 010's `HTTPRoute`s — no
annotation needed on a generated `Service`. It runs with a TXT ownership
registry (`--registry=txt`), a unique `--txt-owner-id`, and
`--domain-filter` scoped to `lab.<root-domain>` — specifically so its
sync-mode reconciliation cannot delete Terraform's ACM DNS-validation
record in the same zone. `--policy=upsert-only` is explicitly rejected as a
substitute for this guard, since it would leave orphaned records behind on
`make down`. It gets its own EKS Pod Identity association, scoped to
`route53:ChangeResourceRecordSets`/`ListResourceRecordSets` on the lab
zone's ARN — noting that `route53:ListHostedZones` cannot be
resource-scoped (an AWS IAM API constraint) and must remain `*`.

**AWS Load Balancer Controller and ExternalDNS each get their own EKS Pod
Identity association**, following the `karpenter-pod-identity`/
`ebs-csi-pod-identity` precedent — not IRSA, per the constitution's
"prefer EKS Pod Identity for new components" and ADR 0001.

## Consequences

- Spec 011 ("Public Edge") is renamed `011-nlb-edge` and rewritten around
  this design; spec 012 becomes a new, dedicated ExternalDNS spec (the
  former 012–023 specs shift to 013–024 to make room, following the same
  mechanical renumbering already used once in this repository for the
  Debezium move).
- Constitution §3, §7, §8, §14, §16, and §18, plus `CLAUDE.md`'s platform
  architecture section, are reworded from ALB to NLB terminology. No
  binding requirement's *meaning* changes — the mechanism it names does.
- Spec 010 gains two new requirements (HTTP-only `Gateway` listener,
  `EnvoyProxy` ownership split) and reworded Requirements 1–2; no change to
  its `ClusterIP`-for-`local` requirement, since `aws` keeps
  `LoadBalancer`-type Service by design under this decision (there was no
  double-load-balancer risk to guard against once the ALB was removed
  entirely from the design).
- A future workload needing a raw TCP/non-HTTP protocol path that bypasses
  Envoy (websockets alone do not qualify — Envoy handles HTTP Upgrade
  natively) can request its own additional `Service type=LoadBalancer` —
  trivially supported by this architecture, deliberately not designed for
  now, since this platform has no application workloads yet (constitution
  §1).
