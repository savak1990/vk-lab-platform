# 002 — Persistent Foundation

**Status:** Implemented

**Complexity:** Low–Medium
**Risk:** Medium — persistent-lifecycle resources; mistakes are annoying to unwind but not catastrophic in a lab account.
**Estimated cost:** ~0.5–1 day · AWS runtime cost: Route 53 hosted zone ~$0.50/month, ACM certs free.
**Recommended model:** Sonnet — standard AWS networking/Terraform, low ambiguity.
**Depends on:** 001-bootstrap (state backend, IAM role for this stack, decrypt-and-supply mechanism for the root domain value)
**Lifecycle class(es) touched:** Persistent

## Scope

Creates the AWS resources that must outlive `make down`:

- A Route 53 public hosted zone for the platform's **delegated subdomain**, `lab.<root-domain>` — NOT the existing root/parent hosted zone, which is external infrastructure outside this repository (constitution §14, ADR 0002).
- An ACM certificate covering `lab.<root-domain>` and `*.lab.<root-domain>`, in the same AWS region as the NLB (spec 011), DNS-validated against the `lab.<root-domain>` zone created here.
- Empty/skeleton AWS Secrets Manager structure (the actual runtime secret values are populated in spec 013).
- `make persistent-up` / `make persistent-down` Makefile targets (constitution §17) wrapping `terragrunt run --all apply`/`destroy` on `terraform/live/persistent/`. `make persistent-down` permanently deletes the lab DNS zone (and its parent-zone NS delegation record), its ACM certificate, everything in Secrets Manager, and retained EBS volumes — it is a deliberate, rarely-used, explicitly-confirmed command, never a side effect of `make down`.

Excludes: **a dedicated VPC** — deliberately out of scope for now. EKS (spec 003) runs in the AWS account's default VPC/default public subnets instead, to keep the first several specs simple. A dedicated persistent VPC is introduced later, as its own spec (020), once the rest of the platform is working. Also excludes: EKS and any Kubernetes-facing resource (003+), RDS (not used — Postgres is in-cluster per project decision), the NLB itself and any DNS record inside the lab zone (011 — those are disposable), and the parent/root hosted zone itself (external, never created/deleted by this repo). The single NS record delegating `lab.<root-domain>` from that parent zone **is** Terraform-managed by this stack (constitution §14, ADR 0002) — narrower than "manages the parent zone," but no longer excluded.

## Requirements

1. The `lab.<root-domain>` Route 53 hosted zone, its ACM certificate, and Secrets Manager MUST be Persistent-lifecycle — created by `terraform/live/persistent/` and MUST survive a disposable-stack destroy (constitution §3, §14, architecture.md §6, §12).
2. This spec MUST NOT create a VPC, subnets, or any networking resource — that is spec 021's scope. Nothing here should assume or reference a platform-owned VPC.
3. ACM certificate validation MUST be automated via Route 53 DNS validation records against the `lab.<root-domain>` zone (both Terraform-managed, so no manual console step) — not against the parent zone, and not by reusing the existing root-domain certificate (constitution §14).
4. This stack MUST NOT create, delete, or manage any record inside the parent/root hosted zone other than the single NS record delegating `lab.<root-domain>` (constitution §14) — it creates the delegated `lab.<root-domain>` zone itself, plus that one delegation record; it MUST NOT create or delete the parent zone, and MUST NOT read or write any other record inside it. The parent zone is located by name (`data "aws_route53_zone"`, `private_zone = false`), not by an explicit zone-ID input — accepted trade-off: broader (`ListHostedZones`/`GetHostedZone`, account-wide) IAM instead of a single-zone-scoped grant, and a residual (mitigated, not eliminated) risk if more than one public zone shares the root domain's name in the account. If the real root domain has no Route 53 API to reach (registrar/other DNS provider), this stack's delegation record cannot be created and delegation remains a one-time external/manual step instead.
5. This stack MUST NOT create or manage any Kubernetes resource — it is pure AWS infrastructure (constitution §2).
6. The root domain value (used to name the `lab.<root-domain>` zone and certificate, and to locate the parent zone for delegation) MUST be supplied to Terraform as a decrypted value from the bootstrap KMS-encrypted config mechanism (spec 001) — `secrets/<project>/root-domain.enc`, decrypted directly inside Terraform via the AWS provider's `aws_kms_secrets` data source (not via a shell-exported `TF_VAR_root_domain`) — and MUST NOT appear in any committed `.tfvars`, YAML, Helm values, or documentation. This is the first spec in the roadmap that actually consumes that mechanism, and the first to decrypt inside Terraform rather than via `scripts/secret-decrypt.sh`. This requirement governs workstation/local `terraform apply` only.
7. GitHub Actions workflows that need the root domain value (spec 016, 019) MUST decrypt the committed `secrets/root-domain.enc` in-workflow via `scripts/secret-decrypt.sh`, the same mechanism as Requirement 6 — not via a separate GitHub secret (superseded by ADR 0023; see ADR 0007 for the original, now-obsolete rationale).
8. Because the domain value ends up in Route 53/ACM resource attributes, it will appear in this stack's Terraform state; the persistent stack's remote state MUST be treated as a private, access-controlled artifact — the domain cannot be fully hidden from state (constitution §14).
9. Every resource here MUST carry the platform's standard tags (constitution §16) with `Lifecycle=persistent`, inherited from this stack's `default_tags` provider block.
10. `make up` (spec 014) MUST verify this stack's resources already exist before creating any Disposable-lifecycle resource, and MUST fail with an actionable error telling the operator to run `make persistent-up` first if they do not (constitution §17) — `make up` MUST NOT create Persistent resources on the caller's behalf.
11. `make persistent-down` MUST refuse to run while any Disposable-lifecycle resource still exists — in particular, the disposable-created DNS records inside the `lab.<root-domain>` zone (spec 011) MUST already be gone, since they reference a zone this command is about to delete (constitution §7, §17). `make persistent-down` MUST require an explicit confirmation step beyond just invoking the command, since it permanently deletes the lab DNS zone (and its parent-zone NS delegation record, per Requirement 4), its certificate, all Secrets Manager contents (spec 013), and retained EBS volumes (specs 005/007/025). It MUST verify after destroying that no unit's Terraform state still holds resources, rather than reporting success on a partial destroy — the delegation record's removal is coupled to the same `route53` unit's destroy as the zone itself, so a partial failure there could otherwise leave an orphaned zone with a live parent-zone delegation.

## Implementation hints

- `terraform/live/persistent/` is a separate Terragrunt stack from disposable, with its own state file (per spec 001's state boundary work) — this is the enforcement mechanism for "disposable destroy can't touch persistent."
- Set this stack's `default_tags` provider block to inherit the bootstrap-established pattern (spec 001, constitution §16) with `Lifecycle=persistent` — don't hand-tag individual resources; state separation is the real safety net, tags are for identification and cost dashboards.
- Delegating `lab.<root-domain>` from the parent zone (the parent zone's NS records pointing at this zone's name servers) is created by the `route53` unit itself, via a `data "aws_route53_zone" { name = <root-domain>; private_zone = false }` lookup plus one `aws_route53_record` of type `NS` — provided the parent zone is a Route 53 zone reachable with the same credentials. This requires a pre-existing public hosted zone for the root domain in the target AWS account; if that assumption doesn't hold (registrar/other DNS provider), delegation falls back to the original manual one-time step outside `terraform apply`. Either way, this is documented as a bootstrap prerequisite, not something `make up` automates.
- Use `terraform/live/persistent/route53/` for the delegated zone (and its NS delegation record) and `terraform/live/persistent/acm/` for the certificate, per the repo layout in architecture.md §5 — both consume the decrypted root domain value from spec 001's mechanism, decrypted inside Terraform. The `acm` unit depends on `route53`'s outputs (`zone_id`, `fqdn`) via a Terragrunt `dependency` block, so `terragrunt run --all apply` orders them correctly with no custom sequencing script. The ACM certificate's region must match whatever region spec 003 puts EKS/the NLB in — since both currently land in the account's default VPC region, this is a naming/variable-consistency concern, not a networking one.
- `make up`'s precondition check (Requirement 10) can be as simple as a `terragrunt output` or remote-state-existence check against `terraform/live/persistent/` before proceeding to `terraform/live/cluster/` — no new tooling needed, just an explicit early-exit step in the Makefile target built out fully in spec 014.
- `make persistent-down`'s precondition check (Requirement 11) can reuse spec 014's own postcondition-checklist approach: confirm the disposable stack's EKS/NLB/Karpenter-tagged resources are absent before allowing `terragrunt destroy` on this stack to proceed. Confirmation itself is terragrunt/terraform's own interactive destroy prompt (typing "yes") — the same approach `bootstrap-down.sh` already uses — rather than a separately hand-rolled prompt; it already requires more than a bare `y/n`, satisfying "an explicit confirmation step beyond just invoking the command" without extra custom code.

## Testing / acceptance criteria

- `terraform plan`/`apply` succeeds against the persistent stack's own state, creating `lab.<root-domain>` and its parent-zone NS delegation record without creating, deleting, or modifying any other part of the parent zone.
- The `lab.<root-domain>` hosted zone exists after persistent bootstrap, and the parent zone gains exactly one new NS record for `lab.<root-domain>` pointing at the new zone's 4 name servers.
- NS delegation resolves publicly (e.g., `dig NS lab.<root-domain>` resolves to the lab zone's name servers) immediately after `make persistent-up`, with no manual step in between, when the parent zone is a Route 53 zone reachable with the same credentials; documented as a manual bootstrap prerequisite only in the fallback case (parent zone at a registrar/other DNS provider).
- ACM certificate for `lab.<root-domain>`/`*.lab.<root-domain>` reaches `ISSUED` status via DNS validation against the lab zone in the same `make persistent-up` run, without manual console intervention.
- Confirm no Terraform resource or provider call in this stack creates, deletes, or modifies any parent-zone resource other than the single delegation NS record — no other record is read or written, and the zone itself is never created or deleted.
- Confirm the IAM policy used grants only `route53:ListHostedZones`/`route53:GetHostedZone` (for the name-based lookup) and `route53:ChangeResourceRecordSets`/`route53:GetChange` on the resolved zone — no broader Route 53 write access.
- Fast validation only (fmt, validate, plan, security scan) for the routine create path — this spec has no disposable-stack coupling yet, so there's nothing to destroy/recreate against on every change. The real persistence proof comes once EKS/workloads exist (spec 005 onward) and can be destroyed around this foundation; spec 014's full lifecycle test additionally proves `make down`/`make up` never touch the lab zone, certificate, or parent zone.
- Running `make up` before `make persistent-up` has ever been run fails fast with a clear, actionable error naming `make persistent-up` — it does not create Persistent resources implicitly and does not proceed to create any Disposable resource (Requirement 10).
- **Persistent teardown (deliberate, run once, not part of routine CI):** with the disposable stack still up, attempting `make persistent-down` is refused (Requirement 11). After `make down` tears down the disposable stack, `make persistent-down` — after its explicit confirmation step — successfully deletes the `lab.<root-domain>` hosted zone, its parent-zone NS delegation record, its ACM certificate, every secret in Secrets Manager (spec 013), and every retained EBS volume (specs 005/007/025). Confirm via the AWS console/API that all of these are actually gone, not just that Terraform reported success (Requirement 11's post-destroy state check), and confirm the parent/root hosted zone itself and every other record inside it are untouched throughout.
